~80% lower LLM cost

LLM cost optimisation with model routing

Enterprise market-intelligence platform

The problem. Production LLM workloads ran on premium hosted models, so cost grew with every call.

What I did. Put every chat, embedding and web-search call behind a LiteLLM gateway and moved workloads to a self-hosted open-weights model (Gemma). A fallback chain sends a request to a paid model when the self-hosted one errors, times out or returns invalid JSON, so answers stay usable. Virtual keys attribute cost to each pipeline, and a test fails if any code calls a provider directly. Developed to GDPR compliance requirements.

Result. LLM spend down by about 80%, with no change in what users see.

Built with LiteLLM, Gemma, FastAPI and Python.

842 / 968 injected errors corrected, with no wrong corrections

Guardrails and evaluation for LLM-written emails

Scheduled market briefings with cited sources

The problem. Now and then a briefing credited one company's news to another. The prompt was right in 14 of 14 controlled runs, so more prompt text would not fix a rare model slip.

What I did. Built a deterministic post-generation guardrail. It checks each claim's subject against who owns the sources it cites, and relabels the claim when the evidence clearly belongs to one other company. It fails open and has a kill switch. I evaluated it with a mutation test, injecting 968 wrong subjects into 8 real emails. The test also exposed a sentence splitter that broke claims at abbreviations, which I fixed.

Result. 842 of 968 injected errors corrected. The other 126 were ambiguous multi-company cases the guard is designed to skip. Untouched emails came out unchanged.

Built with Python, mutation testing and replays of real emails.

0.95 run-to-run consistency (Jaccard), p95 latency 6.0 s

Consistent retrieval in a RAG system

Backend behind 26 business AI agents

The problem. The RAG backend runs vector search, LLM query rewriting and an LLM relevance pass over an internal data lake. The same question returned 31, 124 or 154 sources on different runs. The relevance model looped until its token limit, 28% of requests timed out, and the timeout fallback kept almost everything.

What I did. Measured retrieval consistency as run-to-run overlap and compared models offline: 0.93 for the chosen model against 0.57 for the alternative. I switched the relevance model, set the request format per model, rejected truncated outputs, and logged finish reasons and token counts so the failure would show up in monitoring.

Result. A replay of 7 real candidate pools, 5 runs each: 35 of 35 usable, overlap 0.95, p95 latency 6.0 s.

Built with vector search, query rewriting, FastAPI and an offline replay harness.
